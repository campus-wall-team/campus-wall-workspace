# 数据流图

本文档描述校园墙系统中几个核心业务场景的数据流向，帮助开发者理解请求在各个服务间的流转过程。

## 1. 用户发帖流程

```
用户 (前端)
    │
    │ POST /api/v1/posts/publish
    │ { content, categoryId, images[] }
    ▼
campus-wall-frontend
    │
    │ 1. 上传图片到 MinIO
    │    POST /api/v1/files/upload
    ▼
campus_wall
    │
    ├──► 2. 敏感词预检
    │    读取 sensitive-words.txt
    │    匹配 → 直接拒绝 / 未命中 → 继续
    │
    ├──► 3. AI 复审（如命中可疑规则）
    │    本地优先 Chat（qwen2.5:7b / 内网 Qwen3.6-35B），云端 qwen-plus 兜底
    │    判定 → 通过 / 待审核 / 拒绝
    │
    ├──► 4. 保存帖子到 MySQL
    │    INSERT INTO post（含 boardType / price / salary / tags 等板块字段）
    │
    ├──► 5. 写入 Redis 缓存
    │    热帖列表 / 最新帖子
    │
    ├──► 6. 异步入知识图谱
    │    带图帖先 VLM describe_image 生成图片描述
    │    POST /ingest-post → campus-wall-ai:8011（PII 脱敏后写 Post/Item + campus_post_vector）
    │
    └──► 7. 返回响应
         { code: 200, data: postId }
```

**流程说明**：
1. 用户在前端编辑帖子内容并上传图片
2. 前端先上传图片到 MinIO，获取 URL
3. 提交帖子时，后端进行敏感词预检
4. 如命中可疑规则，调用 AI 进行二次审核
5. 审核通过后保存到 MySQL，同时更新 Redis 缓存
6. 返回帖子 ID 给前端

## 2. AI 学长问答流程（Agent 单一入口）

> 旧端点 `/api/v1/ai/chat`、`/ai-senior/chat`、`/chat/stream` 已下线。AI 已收口为**单一入口** `POST /api/v1/ai-senior/agent`（AgentController，强制 JWT 鉴权，userId 取自 `@RequestAttribute`）。

```
用户 (前端)
    │
    │ POST /api/v1/ai-senior/agent
    │ { question, conversationId? }   (Authorization: Bearer)
    ▼
campus_wall (ai.agent 包：轻量 Planner-Executor)
    │
    ├──► 1. 读短期记忆 (ConversationMemoryService → ai_chat_record)
    │       + 指代消解 (QuestionContextualizer)
    │
    ├──► 2. 规划 (Planner)：判定走「找帖」还是「知识问答」
    │
    ├──► 3. 执行只读工具 (ToolExecutor)
    │    ┌───────────────┬──────────────────────┐
    │    ▼               ▼
    │  search_posts    knowledge_qa
    │  工具             工具
    │    │               │
    │  POST            POST
    │  /match-posts    /query
    │    │               │
    │    ▼               ▼
    │  campus-wall-ai (:8011)
    │    │               │
    │  本地 bge-m3 向量化 → Neo4j 向量检索
    │  /match-posts: campus_post_vector 召回帖子 + 匹配理由
    │  /query: campus_chunk_vector 检索 Chunk + 图遍历
    │    │               │
    │  Chat 本地优先 (qwen2.5:7b / 内网 Qwen3.6-35B)，云端 qwen-plus 兜底
    │    │               │
    │    └───────┬───────┘
    │            ▼
    ├──► 4. RelevanceJudge 反幻觉判定
    │       结构化输出收 List<Long>（裸 postId 数组），从严放行真正相关帖子
    │
    ├──► 5. 严格接地合成 (Synthesizer)
    │
    ├──► 6. 异步沉淀长期记忆 (MemoryExtractor.extractAsync → ai_user_memory)
    │
    └──► 7. 返回给前端
          { success, answer, posts[匹配帖子卡片], plan[调试], conversationId }
```

**流程说明**：
1. 前端调用单一 agent 入口，JWT 强制鉴权；后端读短期上下文并做指代消解
2. Planner 规划本轮该「自然语言找帖」还是「知识问答」
3. ToolExecutor 执行只读工具：`search_posts`→campus-wall-ai `/match-posts` 召回帖子；`knowledge_qa`→campus-wall-ai `/query` 知识问答
4. campus-wall-ai 用本地 bge-m3 向量化问题，在 Neo4j 原生向量索引检索，Chat 模型本地优先（qwen2.5:7b / 内网 Qwen3.6-35B）、云端 qwen-plus 兜底
5. **RelevanceJudge 反幻觉判定**从严过滤召回帖，杜绝无关帖误匹配
6. Synthesizer 严格接地合成答案，异步抽取并沉淀长期用户记忆
7. 返回 answer + 匹配帖子卡片 + conversationId

## 3. 内容审核流程

```
用户发帖 / 评论
    │
    ▼
campus_wall
    │
    ├──► 1. 敏感词过滤 (实时)
    │    加载 sensitive-words.txt
    │    DFA 算法匹配
    │         │
    │    ┌────┴────┐
    │    ▼         ▼
    │  通过      命中
    │    │         │
    │    ▼         ▼
    │ 继续     标记待审核 / 直接拒绝
    │    │
    ├──► 2. AI 复审 (可疑内容)
    │    命中规则但不确定时
    │    本地优先 Chat 判定（qwen2.5:7b / 内网 Qwen3.6-35B），云端 qwen-plus 兜底
    │         │
    │    ┌────┼────┐
    │    ▼    ▼    ▼
    │   通过  可疑  违规
    │    │    │    │
    │    ▼    ▼    ▼
    │  发布  人工  拒绝
    │       审核
    │
    └──► 3. 管理后台人工审核 (monitor-ui)
         审核员查看待审核队列
              │
         ┌────┴────┐
         ▼         ▼
       通过      拒绝
         │         │
         ▼         ▼
       发布    删除+通知
```

**审核状态流转**：
```
已发布(PUBLISHED) ◄────┬──── 已拒绝(REJECTED)
       ▲               │            ▲
       │               │            │
       │         人工审核通过    人工/AI 拒绝
       │               │            │
       │               ▼            │
       └──────── 待审核(PENDING) ───┘
                  ▲
                  │
              AI 复审标记
```

## 5. 数据管道流程（ETL → GraphRAG）

```
campus_wall MySQL
    │
    │ 1. 提取数据
    ▼
campus-wall-data-pipeline
    │
    ├──► 2. 数据清洗 (clean.py)
    │    - 去除广告/噪声
    │    - 过滤无效内容
    │    - 识别问答模式
    │
    ├──► 3. 数据脱敏 (PII 移除)
    │    - 手机号/身份证/银行卡 → [电话][身份证][银行卡]
    │    - 邮箱/QQ/微信号 → [邮箱][QQ][微信号]
    │    - @提及 → @某同学；真实姓名 → [姓名]
    │    - 宿舍/学号/链接 → [宿舍][学号][链接]；#接龙整条丢弃
    │
    ├──► 4. 格式转换 (schema.py)
    │    - 统一为 KnowledgeUnit 格式
    │    - 提取问答对
    │
    │ 5. 输出模式选择
    │    ┌─────────┬─────────┐
    │    ▼         ▼         ▼
    │   JSONL    手动审查   --push
    │  (dry-run)  (人工)   (自动推送)
    │    │         │         │
    │    ▼         ▼         ▼
    │  本地文件   确认后    HTTP POST
    │            推送      /index
    │                      │
    │                      ▼
    │              campus-wall-ai (:8011)
    │                      │
    │                      ├──► 分块 (chunking)
    │                      ├──► 实体关系抽取 (本地优先 Chat)
    │                      ├──► 向量化 (bge-m3, 1024 维)
    │                      └──► 写入 Neo4j
    │                           (Document-[:HAS_CHUNK]->Chunk
    │                            Document-[:MENTIONS]->Entity
    │                            campus_chunk_vector 索引)
```

**流程说明**：
1. 数据管道从 campus_wall 的 MySQL 中提取帖子和评论数据
2. 进行数据清洗：过滤广告、噪声，识别有效问答
3. 进行数据脱敏：保护用户隐私，移除 PII 信息
4. 默认 dry-run 模式输出 JSONL 文件供人工审查
5. 确认无误后使用 `--push` 推送到 campus-wall-ai（端口 8011）
6. campus-wall-ai 对文档分块、抽取实体关系、生成向量嵌入，存入 Neo4j

## 6. 带图帖入图谱 + AI 召回流程（VLM 多模态）

> 发帖（尤其带图）后异步进入知识图谱，使其能被 AI 学长用自然语言检索匹配。

```
用户发带图帖 (前端)
    │
    │ POST /api/v1/posts/publish { content, images[], boardType, tags }
    ▼
campus_wall
    │
    ├──► 1. 帖子落库 + 图片入 MinIO（见「用户发帖流程」）
    │
    ├──► 2. 异步入图谱 POST /ingest-post
    │    { post_id, intent, category?, text, images, tags }
    ▼
campus-wall-ai (:8011)
    │
    ├──► 3. VLM describe_image 读图
    │    本地 qwen2.5vl:7b（云端 qwen-vl-plus 兜底）
    │    生成图片文字描述
    │
    ├──► 4. PII 脱敏 (sanitize.py)
    │    对「用户文字 + VLM 图片描述」统一抹除手机号/微信号/学号等
    │
    ├──► 5. 向量化 (bge-m3) + 写 Neo4j
    │    Post-[:DESCRIBES]->Item、Post-[:HAS_INTENT]->Intent
    │    Post-[:IN_CATEGORY]->Category、Post-[:TAGGED]->Tag
    │    Item embedding 入 campus_post_vector 索引
    │
    └──► 6. 返回 { post_id, item_id, description, indexed }

         ……稍后，用户向 AI 学长提问……

AI 学长 (POST /api/v1/ai-senior/agent)
    │
    └──► search_posts 工具 → POST /match-posts
         campus_post_vector 召回相关帖子（含图片描述）
         RelevanceJudge 从严过滤 → 以卡片回填前端
```

**流程说明**：
1. 用户发布带图帖，后端落库并上传图片到 MinIO
2. 异步调 campus-wall-ai `/ingest-post` 入图谱
3. campus-wall-ai 用本地 VLM（qwen2.5vl:7b，云端 qwen-vl-plus 兜底）`describe_image` 读图生成描述
4. `sanitize.py` 对用户文字 + 图片描述统一 PII 脱敏后再入库
5. 文本与图片描述一起向量化（bge-m3），写入 Post/Item 节点及 `campus_post_vector` 索引
6. 之后 AI 学长 agent 通过 `/match-posts` 即可按自然语言召回这些帖子（含"看图"语义），经 RelevanceJudge 过滤后回填前端

## 数据流总结表

| 业务场景 | 涉及服务 | 数据存储 | 关键接口 |
|----------|----------|----------|----------|
| 用户发帖 | 前端 → 后端 → MinIO/MySQL/Redis（异步入图谱） | MySQL, MinIO, Redis, Neo4j | POST /api/v1/posts/publish |
| AI 问答 | 前端 → 后端 ai.agent → campus-wall-ai(:8011) → Neo4j/LLM | MySQL (ai_chat_record / ai_user_memory) | POST /api/v1/ai-senior/agent |
| 实时私信 | 前端 ↔ 后端 WebSocket → MySQL | MySQL (消息) | ws://host/ws/chat |
| 内容审核 | 后端 AI 审核 → monitor-ui 人工 | MySQL | 内部 + /api/v1/admin/moderation |
| 数据管道 | MySQL → pipeline → campus-wall-ai(:8011) → Neo4j | Neo4j | POST /index |
| 带图帖入图谱 | 后端 → campus-wall-ai(:8011)（VLM 读图 + 脱敏） → Neo4j | Neo4j (campus_post_vector) | POST /ingest-post、/match-posts |
| 监控告警 | Exporters → Prometheus → Alertmanager | - | Webhook /alert |
