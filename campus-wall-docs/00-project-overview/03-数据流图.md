# 数据流图

本文档描述校园墙系统中几个核心业务场景的数据流向，帮助开发者理解请求在各个服务间的流转过程。

## 1. 用户发帖流程

```
用户 (前端)
    │
    │ POST /api/v1/posts/publish
    │ { content, categoryId, images[] }
    ▼
campus-wall-frontend
    │
    │ 1. 上传图片到 MinIO
    │    POST /api/v1/files/upload
    ▼
campus_wall
    │
    ├──► 2. 敏感词预检
    │    读取 sensitive-words.txt
    │    匹配 → 直接拒绝 / 未命中 → 继续
    │
    ├──► 3. AI 复审（如命中可疑规则）
    │    调用 DashScope/qwen-plus
    │    判定 → 通过 / 待审核 / 拒绝
    │
    ├──► 4. 保存帖子到 MySQL
    │    INSERT INTO post
    │
    ├──► 5. 写入 Redis 缓存
    │    热帖列表 / 最新帖子
    │
    └──► 6. 返回响应
         { code: 200, data: postId }
```

**流程说明**：
1. 用户在前端编辑帖子内容并上传图片
2. 前端先上传图片到 MinIO，获取 URL
3. 提交帖子时，后端进行敏感词预检
4. 如命中可疑规则，调用 AI 进行二次审核
5. 审核通过后保存到 MySQL，同时更新 Redis 缓存
6. 返回帖子 ID 给前端

## 2. AI 学长问答流程（GraphRAG）

```
用户 (前端)
    │
    │ POST /api/v1/ai/chat
    │ { message, sessionId }
    ▼
campus-wall-frontend
    │
    │ POST /api/v1/ai/chat
    ▼
campus_wall
    │
    ├──► 1. 检查用户 AI 使用配额
    │
    ├──► 2. 保存用户消息到 MySQL (chat_record)
    │
    ├──► 3. 构造查询请求
    │    { question, history: [...] }
    │    │
    ▼    ▼
campus-wall-graphrag (:8001)
    │
    ├──► 4. 向量化用户问题
    │    调用 Ollama/bge-m3 (本地 11434)
    │    获取 1024-dim 向量
    │
    ├──► 5. 向量检索 + 图遍历 (Neo4j)
    │    相似度搜索相关 Document Chunk
    │    图遍历获取关联实体和关系
    │
    ├──► 6. 构造 Prompt (检索结果 + 历史)
    │
    ├──► 7. 调用 Chat LLM 生成回答
    │    DashScope/qwen-plus
    │
    └──► 8. 返回回答
         { answer, sources }
              │
              ▼
campus_wall
    │
    ├──► 9. 保存 AI 回复到 MySQL
    │
    └──► 10. 返回给前端
          { code: 200, data: { answer, sessionId } }
```

**流程说明**：
1. 用户在 AI 聊天界面发送问题
2. 后端先检查用户的 AI 使用配额和偏好设置
3. 将用户问题转发给 GraphRAG 服务
4. GraphRAG 使用本地 Ollama bge-m3 将问题转换为向量
5. 在 Neo4j 中进行向量相似度搜索 + 图遍历，获取相关上下文
6. 将检索结果 + 对话历史构造为 Prompt
7. 调用 DashScope qwen-plus 生成回答
8. 保存对话记录，返回给前端

## 3. 内容审核流程

```
用户发帖 / 评论
    │
    ▼
campus_wall
    │
    ├──► 1. 敏感词过滤 (实时)
    │    加载 sensitive-words.txt
    │    DFA 算法匹配
    │         │
    │    ┌────┴────┐
    │    ▼         ▼
    │  通过      命中
    │    │         │
    │    ▼         ▼
    │ 继续     标记待审核 / 直接拒绝
    │    │
    ├──► 2. AI 复审 (可疑内容)
    │    命中规则但不确定时
    │    调用 qwen-plus 判定
    │         │
    │    ┌────┼────┐
    │    ▼    ▼    ▼
    │   通过  可疑  违规
    │    │    │    │
    │    ▼    ▼    ▼
    │  发布  人工  拒绝
    │       审核
    │
    └──► 3. 管理后台人工审核 (monitor-ui)
         审核员查看待审核队列
              │
         ┌────┴────┐
         ▼         ▼
       通过      拒绝
         │         │
         ▼         ▼
       发布    删除+通知
```

**审核状态流转**：
```
已发布(PUBLISHED) ◄────┬──── 已拒绝(REJECTED)
       ▲               │            ▲
       │               │            │
       │         人工审核通过    人工/AI 拒绝
       │               │            │
       │               ▼            │
       └──────── 待审核(PENDING) ───┘
                  ▲
                  │
              AI 复审标记
```

## 5. 数据管道流程（ETL → GraphRAG）

```
campus_wall MySQL
    │
    │ 1. 提取数据
    ▼
campus-wall-data-pipeline
    │
    ├──► 2. 数据清洗 (clean.py)
    │    - 去除广告/噪声
    │    - 过滤无效内容
    │    - 识别问答模式
    │
    ├──► 3. 数据脱敏 (desensitize.py)
    │    - 手机号/身份证号/银行卡号 → ****
    │    - 邮箱/QQ/微信号 → 隐藏
    │    - 真实姓名 → 楼主/同学A/同学B...
    │    - 宿舍号/学号 → 隐藏
    │
    ├──► 4. 格式转换 (schema.py)
    │    - 统一为 KnowledgeUnit 格式
    │    - 提取问答对
    │
    │ 5. 输出模式选择
    │    ┌─────────┬─────────┐
    │    ▼         ▼         ▼
    │   JSONL    手动审查   --push
    │  (dry-run)  (人工)   (自动推送)
    │    │         │         │
    │    ▼         ▼         ▼
    │  本地文件   确认后    HTTP POST
    │            推送      /index
    │                      │
    │                      ▼
    │              campus-wall-graphrag
    │                      │
    │                      ├──► 分块 (chunking)
    │                      ├──► 实体关系抽取 (LLM)
    │                      ├──► 向量化 (bge-m3)
    │                      └──► 写入 Neo4j
    │                           (Document/Chunk/Entity)
```

**流程说明**：
1. 数据管道从 campus_wall 的 MySQL 中提取帖子和评论数据
2. 进行数据清洗：过滤广告、噪声，识别有效问答
3. 进行数据脱敏：保护用户隐私，移除 PII 信息
4. 默认 dry-run 模式输出 JSONL 文件供人工审查
5. 确认无误后使用 `--push` 推送到 GraphRAG
6. GraphRAG 对文档分块、抽取实体关系、生成向量嵌入，存入 Neo4j

## 数据流总结表

| 业务场景 | 涉及服务 | 数据存储 | 关键接口 |
|----------|----------|----------|----------|
| 用户发帖 | 前端 → 后端 → MinIO/MySQL/Redis | MySQL, MinIO, Redis | POST /api/v1/posts/publish |
| AI 问答 | 前端 → 后端 → GraphRAG → Neo4j/LLM | MySQL (聊天记录) | POST /api/v1/ai/chat |
| 实时私信 | 前端 ↔ 后端 WebSocket → MySQL | MySQL (消息) | ws://host/ws/chat |
| 内容审核 | 后端 AI 审核 → monitor-ui 人工 | MySQL | 内部 + /api/v1/admin/moderation |
| 数据管道 | MySQL → pipeline → GraphRAG → Neo4j | Neo4j | POST /index |
| 监控告警 | Exporters → Prometheus → Alertmanager | - | Webhook /alert |
