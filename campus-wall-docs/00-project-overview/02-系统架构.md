# 系统架构

## 整体架构概览

## 服务职责划分

### 1. campus_wall（主后端服务）
**定位**：核心业务后端，所有客户端请求的入口
**职责**：
- 用户认证（微信 OAuth2 + JWT）；学生认证（学生证 OCR + 人工复核）
- 帖子 CRUD、评论、点赞、收藏；5 板块（推荐/二手/兼职/推广/组队）+ 标签 + 排行榜/热搜榜
- AI 学长 Agent（单一入口 `/api/v1/ai-senior/agent`）：现网默认 `ai.agent.remote-enabled=true`，转发到 campus-wall-ai 的 LangGraph 子图（Plan-Execute + 单次条件 replan）；置 false 时兜底回 Java 进程内 Planner-Executor + RelevanceJudge
- 内容审核（敏感词 + AI 复审）
- 私信系统（WebSocket）
- 管理后台 API（独立 admin_user RBAC、操作审计、运营看板、系统配置）
- 定时任务（指标收集、文件清理）

### 2. campus-wall-frontend（多端前端）
**定位**：面向学生的移动端应用
**职责**：
- 帖子浏览与发布
- AI 学长聊天界面
- 私信聊天
- 用户个人中心
- 支持 H5 和微信小程序

### 3. campus-wall-monitor-ui（管理后台）
**定位**：面向管理员的后台管理系统
**职责**：
- 登录认证 + RBAC 权限驱动菜单（Pinia useUserStore + v-permission 指令 + 路由 meta.perms 守卫）
- 内容审核队列、举报处理、意见反馈、学生认证复核
- 用户管理（封禁/解封）、管理员/角色权限管理、系统配置
- 操作审计日志查询
- 运营看板（KPI 卡 + 趋势/分布/热帖图表，vue-echarts）
- 系统监控概览 + Grafana 面板嵌入

### 4. campus-wall-ai（AI 知识图谱服务）

> 原独立服务 campus-wall-graphrag 已并入 campus-wall-ai（端口 8011），下列全部 HTTP 端点路径原样保留。

**定位**：AI 问答核心引擎（9 个 HTTP 端点）
**职责**：
- 接收文档并构建知识图谱（/index）
- 接收问题并返回 AI 回答（/query + /query/stream 流式）
- AI 学长 Agent 子图（LangGraph：指代消解 → 看图说话 → Plan-Execute → 闸/单次条件 replan → 合成）：Java 后端默认转发到此（`ai.agent.remote-enabled=true`），承载 `/ai/chat`、AI 发帖 `/ai/posts/*`
- 帖子入图谱（/ingest-post，含 VLM 图片描述 + PII 脱敏）
- 自然语言匹配帖子（/match-posts，向量召回 + 匹配理由）
- 多模态读图（/describe-image，VLM qwen2.5vl:7b）
- 文档/帖子管理（/documents、DELETE /posts/{id}）、健康检查（/health）
- Neo4j 知识图谱维护与原生向量索引管理（campus_chunk_vector + campus_post_vector）
- Chat（规划/合成/判定/意图/抽取）主用【内网 Qwen3.6-35B @ 172.21.160.101:8003】，与原 Java agent 一致，无云端兜底默认关闭；本地 Ollama 仅承担 Embedding (bge-m3) 与 VLM (qwen2.5vl:7b)，VLM 可云端 DashScope 降级

### 5. campus-wall-data-pipeline（数据管道）
**定位**：ETL 数据处理器
**职责**：
- 从 campus_wall MySQL 提取帖子数据
- 数据清洗（去噪、去广告）
- 数据脱敏（PII 信息移除）
- 推送到 campus-wall-ai（端口 8011）构建知识图谱

### 6. campus-wall-ops（运维配置）
**定位**：基础设施即代码
**职责**：
- Docker Compose 编排所有基础设施服务
- Prometheus 监控配置
- Grafana 面板配置
- Alertmanager 告警规则
- Nginx 反向代理配置

#### 告警适配器（campus-wall-ops/alert-adapter 子目录）
**定位**：告警通知转发服务（仍是名为 alert-adapter 的容器/服务，:9094；源码已并入 ops 子目录，不再是独立仓库）
**职责**：
- 接收 Alertmanager 的 webhook 告警
- 转换为企微/钉钉消息格式
- 发送到对应的群聊

## 部署拓扑

### 开发环境（团队内网，A机 + B机分工）

实际落地为内网两机分工，而非单机：

```
[A机：GB10 服务器 / 172.21.160.212 / 121G 内存 / 主机名 spark-ab42]
  集中：所有中间件 + AI 服务容器 + 模型
  ├── campus-wall-ai (端口 8011；连本机 Neo4j/Redis/bge-m3 一律用 localhost)
  ├── campus-wall-ops/docker-compose.yml (所有基础设施容器)
  │     ├── MySQL :3306（多库：campus_wall / _dev_a / _dev_b / _test）
  │     ├── Redis :6379（逻辑库：0=prod / 1=dev_a / 2=dev_b / 15=test）
  │     ├── MinIO :9000/9001（bucket：campus-wall / campus-dev-a / campus-dev-b / campus-test）
  │     ├── Neo4j（三实例：prod 7688 / test 7689 / dev 7691，对应容器 neo4j / neo4j-test / neo4j-dev）
  │     ├── Prometheus :9090
  │     ├── Grafana :3000
  │     └── ...
  └── Ollama :11434（仅绑 A机 localhost，未对 LAN 暴露：bge-m3 embedding + qwen2.5vl:7b VLM）

[B机及各开发机]
  跑 Java 后端 + 前端，连 A机 中间件用内网 IP 172.21.160.212
  ├── campus_wall (本地启动，端口 8080；SPRING_PROFILES_ACTIVE=dev/test/prod)
  ├── campus-wall-frontend (npm run dev:h5，端口随 Vite 分配)
  └── campus-wall-monitor-ui (npm run dev，端口随 Vite 分配)

[.101 另一台主机] 内网 Qwen3.6-35B @ 8003（Chat 主力，OpenAI 兼容）
```

> 三环境隔离（dev/test/prod 已落地）：Neo4j 7688/7689/7691、MySQL campus_wall/_dev_a/_dev_b/_test、
> Redis 逻辑库 0/1/2/15、MinIO bucket campus-wall/campus-dev-a/campus-dev-b/campus-test。
> 团队约定 dev 每人一套、test/prod 全队共享。AI 服务切环境用 `APP_ENV=dev/test/prod`
> （config.py 自动加载 `.env.<env>`），Java 用 `SPRING_PROFILES_ACTIVE` + `application-{dev,test,prod}.yaml`。
> 详见 [20-operation/03-团队内网开发指南](../20-operation/03-团队内网开发指南.md)
> 与 [01-development-standards/全栈开发流程与三环境切换](../01-development-standards/全栈开发流程与三环境切换.md)。
