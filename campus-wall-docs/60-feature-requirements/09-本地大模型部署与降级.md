# 09 · 本地大模型部署与降级(本地优先 + 云端 failover)

> AI 基础设施篇,是 [`06`](./06-AI视觉模型与图片标注.md)/[`07`](./07-AI知识入库-Neo4j图谱.md)/[`08`](./08-AI智能推荐与问答.md) 三篇的底座。本篇讲清两件事:**大模型到底怎么部署、怎么被代码调用**;以及本项目统一采用的 **「本地优先 + 云端降级(failover)」** 方案。面向第一次接触大模型 / agent 开发的同学,可循序渐进阅读。

## 一、概述

### 目标与动机
让所有 LLM 调用 **优先走本地 / 内网自部署的模型**(数据不出内网、省钱、低延迟;EMBED/VLM 在本机 Ollama,CHAT 在内网 35B `@.101:8003`),仅当其不可用(连不上 / 超时 / 模型未加载 / 显存不足)时,**自动接口降级到下一级端点直至外部云端 API** 兜底可用性。这是生产级高可用系统的标准套路,业界叫 **failover / 降级**。

### 一句话结论
- **chat(回答/推理)、VLM(图像识别)** 可以自由降级(输出是文字,换模型只是质量差异)。
- **embedding(向量化)不能随便降级**——向量存在 Neo4j 里,降级必须是同一个模型同一维度,否则检索全乱(见 [五](#五️-embedding-降级的硬约束必读))。

## 二、先建立正确的心智模型:大模型 = 一个 HTTP 推理服务

> **一个大模型 = 一个监听某端口的 HTTP 服务。你的程序通过 HTTP 调它,和调一个天气 API 没有本质区别。**

跑一个本地大模型需要两样东西:

1. **模型权重**:几个 GB 的文件(模型"学到的参数")。如 `qwen2.5:7b` ≈ 4.7 GB、`bge-m3` ≈ 1.2 GB。
2. **推理引擎**:把权重加载进显存/内存、对外提供 API 的程序。常见有 **Ollama**(本地最傻瓜)、**vLLM/SGLang**(生产高并发)、llama.cpp(轻量)。

引擎跑起来后监听一个端口(Ollama 默认 `11434`),你的代码往这个端口发 `POST /v1/chat/completions`,它返回模型生成的文字。

### 关键:为什么"换模型"这么简单 —— OpenAI 兼容

业界几乎所有推理引擎与云服务,都模仿了 **OpenAI 的 API 格式**(`/v1/chat/completions`、`/v1/embeddings`)。所以你的代码只认三个参数:

| 参数 | 含义 | 端点示例 | 云端示例 |
|------|------|---------|---------|
| `base_url` | 服务地址 | `http://172.21.160.101:8003/v1`(内网 35B) / `http://localhost:11434/v1`(本机 Ollama,EMBED/VLM) | `https://dashscope.aliyuncs.com/compatible-mode/v1` |
| `api_key` | 密钥 | `na` / `ollama`(占位即可) | `sk-...`(真 key) |
| `model` | 模型名 | `Qwen3.6-35B` / `bge-m3` / `qwen2.5vl:7b` | `qwen-plus` |

**换后端 = 只改这三个值,业务代码一行不动。** 本项目 `campus-wall-ai/app/config.py` 的 `CHAT_BASE_URL / CHAT_API_KEY / CHAT_MODEL` 一整套环境变量,设计的就是这件事——这也正是"本地/内网优先 + 云端降级"能轻松实现的根本原因:降级无非是准备**多套**这样的三元组(chat 备了两套:本地 8005 + 云端)。

## 三、三套独立的 LLM 角色(各自本地主 + 云端降级)

本项目把 LLM 拆成 **三套完全独立的配置**,各自指向不同模型、各自做本地优先 + 云端降级:

| 角色 | 用途 | 主端点 | 降级兜底 | 现状 |
|------|------|---------|--------------|---------|
| **CHAT** | 意图识别 / 规划 / 三元组抽取 / 答案合成 / 相关性判定 | **内网 Qwen3.6-35B** `@172.21.160.101:8003`(OpenAI 兼容,**非**本机 Ollama,与 Java `ai.agent` 一致) | 三级链:8005(`CHAT_FALLBACK`)→云端(`CHAT_FALLBACK2`),**默认均关闭**(.101 宕则不可用) | ✅ 内网 35B 在用 |
| **EMBED** | 向量化(存/读 Neo4j) | 本机 Ollama `bge-m3`(1024 维) | 默认**关闭**(须同模型) | ✅ 已有 bge-m3 |
| **VLM** | 图像物体识别 | 本机 Ollama `qwen2.5vl:7b`(轻量) | `qwen-vl-plus` | ❗需 `ollama pull`(功能落地时) |

**为什么 CHAT 与 VLM 必须分开?** VLM(视觉模型)更吃资源、在纯文本任务上不占优;图像识别要轻量(发帖异步入库要快、量大),回答问题要准(用更大的文本模型)。各取所需。

## 四、本项目的降级实现(贴合真实代码)

### 4.1 campus-wall-ai(Python,原 graphrag 已并入,端口 8011):`_with_fallback` 通用包装

核心在 `campus-wall-ai/app/graphrag/llm.py`。每个角色有一个**主**客户端 + 若干可选的**备**客户端,用一个通用包装把"试主、依次试备"封装起来(现签名为可变参数,支持多级降级链,如 chat 的 8003→8005→云端):

```python
def _with_fallback(role, primary, *fallbacks):
    chain = [primary] + [f for f in fallbacks if f is not None]
    last_exc = None
    for i, fn in enumerate(chain):
        try:
            return fn()
        except Exception as e:                   # noqa: BLE001
            last_exc = e
            tier = "primary" if i == 0 else f"fallback{i}"
            logger.warning("[%s] %s 调用失败: %s", role, tier, e)
    raise last_exc                               # chain 至少含 primary,必有异常
```

`chat()` / `embed()` / `chat_stream()` / `extract_triples()` 都走这个包装。**调用方零改动**:原有的调用点(问答 chat、流式 chat、chunk embed、query embed、三元组抽取)自动获得 failover 能力。其中 `chat()` 传入两个 fallback(本地 8005 + 云端),`embed()` / `chat_stream()` 各传相应级数;两参形式只是其单级特例。

> 流式 `chat_stream` 的降级语义:仅在"打开流 / 首个 token 之前"失败时沿三级链切到下一级流(8005→云端);一旦已 yield 过 token(中途断开)无法干净地从头降级。绝大多数不可用场景(连不上、模型未加载)都在打开流时即抛错,可被覆盖。

### 4.2 Java 内容审核:`FailoverChatClient`

Java 端有两处直连 LLM:**内容审核 AI 复审**(本地优先 + 云端降级)和 **Agent**(轻量 Planner-Executor,直连内网 35B、无云端兜底)。本节讲复审;Agent 走 `AgentConfig` 自建的独立 `ChatClient`,端点 `ai.agent.base-url`=`http://172.21.160.101:8003/v1`(`application.yaml:104-107`),与复审分离、各配各的。

复审入口 `admin/.../ModerationServiceImpl.aiRescore`,实现 `ai/service/FailoverChatClient.java`,用 `RestTemplate` 直调 OpenAI 兼容 `/v1/chat/completions`,本地优先、失败降级云端(与 campus-wall-ai 同思路、全栈统一):

```java
public String complete(String system, String user, double temperature) throws Exception {
    try {
        return callOnce(localBaseUrl, localApiKey, localModel, system, user, temperature);
    } catch (Exception e) {
        log.warn("[chat] 本地模型调用失败: {}", e.getMessage());
        if (!cloudEnabled) throw e;
        log.warn("[chat] 降级到云端 API");
        return callOnce(cloudBaseUrl, cloudApiKey, cloudModel, system, user, temperature);
    }
}
```

> 为什么 Java 不用 Spring AI 的 `ChatModel` 做降级?因为手动构造两个 `OpenAiChatModel`(Spring AI 1.0.8)有版本 API 不确定性,而 `RestTemplate` 是稳定标准库、本地云端共用一套代码,更可控。

### 4.3 配置一览

| 位置 | 配置 | 作用 |
|------|------|------|
| `campus-wall-ai/app/config.py` | `CHAT_*` + `CHAT_FALLBACK_*` + `CHAT_FALLBACK2_*` + `EMBED_*` + `EMBED_FALLBACK_*` + `VLM_*` | campus-wall-ai(原 graphrag 已并入)各角色端点 |
| `campus-wall-ai/.env.{dev,test,prod}.example`、`campus-wall-ops/ai-service/.env.example` | 上述变量的部署模板 | 实际部署填值(`.env` 不入库) |
| `campus_wall/.../application.yaml` | `ai.local.*` + `ai.cloud.*`(复审) + `ai.agent.*`(Agent 直连 35B) | Java 审核本地/云端端点 + Agent 端点 |

关键默认值(`config.py:90-112`,改默认值即生效,因为 ops 的 `ai-service/.env` 当前为空):

```
CHAT_BASE_URL   = http://172.21.160.101:8003/v1   # 内网 Qwen3.6-35B(非本机 Ollama)
CHAT_MODEL      = Qwen3.6-35B
CHAT_FALLBACK_ENABLED    = false                  # 第一级 fallback：本地 8005，默认关
CHAT_FALLBACK_BASE_URL   = https://dashscope.aliyuncs.com/compatible-mode/v1
CHAT_FALLBACK_MODEL      = qwen-plus
CHAT_FALLBACK2_ENABLED   = false                  # 第二级 fallback：云端兜底，默认关
CHAT_FALLBACK2_BASE_URL  = https://dashscope.aliyuncs.com/compatible-mode/v1
CHAT_FALLBACK2_MODEL     = qwen-plus
EMBED_BASE_URL  = http://localhost:11434/v1       # 本机 Ollama
EMBED_MODEL     = bge-m3   (1024 维)
EMBED_FALLBACK_ENABLED   = false                  # ⚠️ 见第五节
VLM_BASE_URL    = http://localhost:11434/v1       # 本机 Ollama
```

> **CHAT 三级降级链**(`config.py:105-112` + `llm.py` 的 `chat_fb_client` / `chat_fb2_client`):
> `8003`(primary,内网 35B) → `8005`(`CHAT_FALLBACK`,本地备) → 云端(`CHAT_FALLBACK2`,兜底)。
> 两级 fallback **默认均关闭**——与 Java `ai.agent` 一致(.101 宕即不可用);要启用须 `CHAT_FALLBACK_ENABLED=true` 并配好 8005/云端端点与 key。EMBED / VLM 仍是本机 Ollama,各自独立降级。

## 五、⚠️ Embedding 降级的硬约束(必读)

向量是**存进 Neo4j 里**的。如果入库时用 bge-m3(1024 维)生成向量,查询时却降级到**另一个** embedding 模型(比如云端 `text-embedding-v3`),两个模型的"向量空间"对不上,**检索会直接失效**(算出来的相似度是乱的)。

因此:

- `EMBED_FALLBACK_ENABLED` **默认 `false`**(关闭)。
- 如要开启,降级目标**必须是同一个 bge-m3**(例如云端自建 / 硅基流动 SiliconFlow 提供的 bge-m3),且 `EMBED_FALLBACK_MODEL` 必须等于 `EMBED_MODEL`、维度等于 `EMBED_DIM`(1024)。
- chat / VLM **没有**这个限制——它们输出文字,换模型只是质量差异、不会"对不上"。

> 本项目 embedding 与 VLM 同在 A 机本机 Ollama(CHAT 主链则在另一台内网 35B,二者不同机)。Ollama 挂了 embedding/VLM 一起挂,而降级目标受同模型同维度硬约束,实际收益有限,默认关闭是稳妥选择。

## 六、在 GB10 上部署本地模型(Ollama 实操)

GB10(NVIDIA Grace Blackwell)统一大内存,本地跑 7B~32B 量化模型从容。

> 注意:本机 Ollama **只负责 EMBED / VLM**;CHAT 主链是内网 Qwen3.6-35B(`@.101:8003`),**不**在本机 Ollama。

### 本机现状(已就绪,无需重复 pull;环境快照以实际 `ollama list` 为准)
```
qwen2.5:7b      4.7 GB   ← 内容审核复审(Java ai.local)本地模型 / CHAT 备用,非 CHAT 主链
bge-m3          1.2 GB   ← EMBED 主模型(向量化,正在用)
nomic-embed-text 274 MB  ← 备用(英文为主,本项目不用)
Ollama 监听 :11434(版本以 ollama list 为准)
```

### 安装 / 拉模型 / 启动 / 验证
```bash
# 1. 安装 Ollama(Linux;装完通常作为 systemd 服务常驻 :11434)
curl -fsSL https://ollama.com/install.sh | sh

# 2. 按需拉模型(已有的不必再拉)
ollama pull qwen2.5:14b     # 可选:升级 CHAT 提质(约 9GB),改 CHAT_MODEL=qwen2.5:14b 即生效
ollama pull qwen2.5vl:7b    # VLM 图像识别功能落地时再拉(约 6GB)

# 3. 确认服务 / 已装模型
systemctl status ollama     # 或手动:ollama serve
ollama list

# 4. 命令行试一下
ollama run qwen2.5:7b "用一句话介绍校园墙"

# 5. 验证 OpenAI 兼容接口(这就是代码要调的东西)
curl http://localhost:11434/v1/chat/completions -d '{
  "model": "qwen2.5:7b",
  "messages": [{"role":"user","content":"你好"}]
}'
```

第 5 步跑通,就证明"本机 Ollama API"已就绪——这台 Ollama 服务的是 **EMBED / VLM**(`EMBED_BASE_URL` / `VLM_BASE_URL` 指向 `http://localhost:11434/v1`)。CHAT 不在此,它指向内网 35B `http://172.21.160.101:8003/v1`(见三/四节)。

> **网络拓扑提醒(EMBED / VLM)**:campus-wall-ai 容器以 `network_mode: host` 运行(`docker-compose.yml:94`),容器内 `localhost` 即 A 机宿主机,因此直接用 `http://localhost:11434/v1` 即可回访宿主机 Ollama,**不再需要 `host.docker.internal` / `extra_hosts`**。bge-m3 / Ollama 仅绑 A 机 localhost(未对 LAN 暴露)。Java 复审若与 Ollama 同机用 `localhost:11434`,跨机则用 GB10 内网 IP(环境变量 `AI_LOCAL_BASE_URL` 覆盖)。CHAT 主链(35B)则始终经局域网直连 `172.21.160.101:8003`。

## 七、故障演练与验收(怎么验证降级真的生效)

1. **正常应答**:`docker compose up -d --build ai-api`(服务名 `ai-api`,容器 `campus-wall-ai`)后调 `/query`,日志无"降级"字样,内网 35B(`@.101:8003`)应答。
2. **chat 降级演练**:先 `CHAT_FALLBACK_ENABLED=true` 并配好 8005 / 云端端点与 key(默认关),再停/坏内网 35B(把 `CHAT_BASE_URL` 指向坏端口,或 .101:8003 宕)→ 再调 `/query` → 日志出现 `[chat] primary 调用失败` 并沿三级链 `fallback1`(8005)→`fallback2`(云端)降级,仍返回答案。未开 fallback 时 primary 失败即报错(与生产一致)。
3. **embedding 不乱降级**:确认入库/检索仍用 bge-m3(向量维度 1024);`EMBED_FALLBACK_ENABLED` 默认关闭。
4. **Java 审核降级**:发一条含 URL 的可疑内容触发 `aiRescore` → 本地优先打分;停本地后降级云端仍打分。
5. **VLM 降级(功能落地后)**:停本地 VLM,`describe_image` 自动降级云端、仍返回结构化 JSON;两端都失败才返回 `{}`(不阻断发帖入库)。

## 八、主流 agent 开发的部署/调用范式(延伸)

### 部署引擎怎么选
| 方式 | 是什么 | 适合 | 难度 |
|------|--------|------|------|
| **Ollama** | 最傻瓜的本地引擎,一行拉模型、自带 OpenAI 兼容 API | 开发、个人、中小规模 ← **本项目现状** | ⭐ |
| **vLLM / SGLang** | 生产级高性能引擎,高并发高吞吐 | 上线扛大流量 | ⭐⭐⭐ |
| **云端 API** | 别人部署好(DashScope/OpenAI) | 不想买卡、要最强模型 | ⭐ |

> Docker 只是打包方式,不是必须:可用 Docker 跑引擎,也可直接装宿主机。对代码而言"引擎在哪"都一样——就是一个 HTTP 地址。本项目 EMBED/VLM 的 Ollama 直接装 A 机宿主机,campus-wall-ai 容器以 host 网络经 `localhost` 回访;CHAT 则是另一台内网机的 35B(`@.101:8003`),经局域网直连。

### 第一次开发 agent 的学习路径
1. **调 LLM 的本质**:发 `messages`(system 设定角色 + user 提问),拿回一段文字。
2. **RAG(检索增强)**:LLM 不懂你的私有数据 → 用 embedding 把帖子变向量存 Neo4j;提问时检索最相关的几条塞进 prompt 让 LLM 参考。**本项目本质就是 RAG 系统。**
3. **function calling**:让 LLM 决定调用某个函数(查库、发请求)——迈向 agent 的关键。
4. **agent loop**:LLM 在"思考→调工具→看结果→再思考"的循环里自主完成多步任务([`08`](./08-AI智能推荐与问答.md) 的"识别意图→检索→推荐"已是雏形)。

## 九、风险与待确认项

1. **单槽串行**:内网 Qwen3.6-35B 是单槽 llama.cpp(`total_slots=1`),同一时刻只处理一个请求;故 SDK 默认关闭重试(`llm.py:36-42`),超时即快速失败,避免把请求怼回已排队的槽位造成雪崩。复审用的本地 `qwen2.5:7b` 比云端 `qwen-plus` 弱,质量有差。
2. **首 token 延迟 / 冷启动**:模型首次加载有延迟;`CHAT_TIMEOUT`(默认 60s)过小可能误触发降级,按机器实测调整。
3. **embedding 降级风险**:见 [五](#五️-embedding-降级的硬约束必读),默认关闭,开启务必同模型同维度。
4. **云端 key 配置**:降级依赖 `CHAT_FALLBACK_API_KEY`/`DASHSCOPE_API_KEY`;未配则本地挂了云端也调不通。
5. **安全(待整改)**:`campus-wall-ai/app/config.py` 的 `NEO4J_PASSWORD`、`application-dev.yaml` 的 `DASHSCOPE_API_KEY` 仍有硬编码默认值,违反"绝不硬编码密钥",建议改为无默认 + 轮换。本批 `.env.example` 已一律用占位符。
