# 团队开发流程指南（小白友好 · 中小团队主流做法）

> 给谁看：第一次进这个项目、对"团队怎么协作开发"没概念的同学。
> 读完你会懂：① 哪台机器干什么；② 后端怎么切 dev/test/prod；③ 两个人怎么用 Git 协作不打架；④ 一个改动从写代码到上线的完整流程。
> 配套：环境切换的细节机制见《全栈开发流程与三环境切换》；评测见《Agent 开发与评测闭环指南》。

## 0. 先把一个误区纠正了 + 机器地图

**常见误区**：以为代码"在哪个仓库就在哪台机器跑"。其实**"代码在哪写"和"程序在哪跑"是两回事**。

| | A机（GB10 / `172.21.160.212` / 121G 内存）| B机（你的开发笔记本，内存小）|
|---|---|---|
| 角色 | **服务器**：跑所有"常驻服务" | **开发机**：写代码 + 跑你正在开发的那个服务 |
| 上面跑什么 | 中间件 MySQL/Neo4j/Redis/MinIO + **AI 服务 campus-wall-ai(容器)** + 模型 Ollama/35B | Java 后端(IDEA 启动) + 小程序前端 + 运营后台前端 |
| 数据 | 在这（持久、共享） | 不存数据，连 A机 |

> 所以：**`campus-wall-ai` 这个 AI 服务确实常驻在 A机**（你把它当成"A机上的一个后端服务"就对了）。你在 B机 改它的代码，但它平时是在 A机 容器里跑的。

**调用关系图**（记住它，调试全靠它）：
```
[B机] 小程序/运营后台前端 ──► [B机] Java 后端(8080) ──► [A机] MySQL/Redis/MinIO
                                      │
                                      └──► [A机] AI 服务 campus-wall-ai(8011) ──► [A机] Neo4j/bge-m3/35B
```
前端只调 Java 后端；Java 后端再去调 A机 的中间件和 AI 服务。**你在 B机 跑的"后端"= Java 后端 `campus_wall`。**

## 1. 三个环境 & 后端怎么切（直接回答你的问题）

### 1.1 三个环境是什么（用"草稿/排练/演出"理解）
| 环境 | 类比 | 给谁 | 数据 |
|---|---|---|---|
| **dev** 开发 | 草稿本 | 你自己 | 假数据，随便造随便删 |
| **test** 测试 | 带妆彩排 | 全队验收 | 干净、可复现的测试数据 |
| **prod** 生产 | 正式演出 | 真实用户 | 真实数据，**碰都别碰测试** |

A机 上这三套中间件已经隔离好了（详见《全栈开发流程与三环境切换》3.4 节）：
- MySQL 库：`campus_wall_dev_a`(你) / `campus_wall_dev_b`(同事) / `campus_wall_test` / `campus_wall`(prod)
- Neo4j 实例：`:7691`(dev) / `:7689`(test) / `:7688`(prod)
- Redis DB 号：1(你) / 2(同事) / 15(test) / 0(prod)

### 1.2 ★ Java 后端（你在 B机 跑的那个）怎么切环境 ★

Java 用 **Spring Profile** 切环境，配置文件是 `application-{dev,test,prod}.yaml`。**切环境 = 选一个 profile，不改代码**。所有中间件地址都是 `${变量:默认值}`，可被环境变量覆盖。

**在 IDEA 里（最常用）**：
1. 右上角运行配置 → Edit Configurations；
2. **Active profiles** 填 `dev`（或 test/prod）；
3. **Environment variables** 填中间件地址（指向 A机）：
   ```
   MYSQL_URL=jdbc:mysql://172.21.160.212:3306/campus_wall_dev_a?characterEncoding=utf8&serverTimezone=Asia/Shanghai
   REDIS_HOST=172.21.160.212
   MINIO_ENDPOINT=http://172.21.160.212:9000
   MINIO_BUCKET=campus-dev-a
   AI_SERVICE_BASE_URL=http://172.21.160.212:8011
   ```
4. 建 3 个运行配置（后端·dev / 后端·test / 后端·prod），以后点一下就切。

**命令行**：
```bash
SPRING_PROFILES_ACTIVE=dev MYSQL_URL=...campus_wall_dev_a REDIS_HOST=172.21.160.212 ... ./mvnw spring-boot:run
```
> ⚠️ 现在只有 `application-dev.yaml` 和 `application-prod.yaml`。要一个干净的 test profile，加一份 `application-test.yaml`（指向 `campus_wall_test` + Redis DB15），或用 dev profile + 上面的环境变量覆盖到 `_test` 库。

### 1.3 其他服务怎么切（一句话版）
| 服务 | 切换方式 |
|---|---|
| **Java 后端** | Spring profile + 环境变量（见上）|
| **AI 服务** | 环境变量 `APP_ENV=dev/test/prod`（config.py 自动加载 `.env.<env>`）|
| **小程序 / 运营后台** | `.env.local` 里 `VITE_API_BASE_URL=http://<Java后端地址>:8080` |

> ⚠️ B机 挂梯子/VPN 会劫持到 A机(172.21.x)的连接 → 配 `export NO_PROXY=localhost,127.0.0.1,172.16.0.0/12`。

## 2. Git 协作：中小团队主流做法（GitHub Flow）

### 2.1 为什么不直接在 main 上改？
`main` 分支代表"随时能上线的稳定版本"。如果两个人都直接往 main 推，你改一半的半成品会污染 main、还会和同事冲突。**主流做法：每个任务开一个独立分支，做完用 PR 合回 main。**

> 这套叫 **GitHub Flow**，是中小团队最常用、最简单的协作模型（比老的 Git Flow 轻量，适合你们 2 人）。

### 2.2 一个改动的完整生命周期
```
①从 main 拉最新 → ②开功能分支 → ③改代码+提交 → ④推到远端开 PR
   → ⑤同事 Code Review → ⑥合并进 main → ⑦删分支
```
```bash
# ① 拉最新
git checkout main && git pull
# ② 开功能分支（命名: 类型/简短描述）
git checkout -b feat/post-search-filter
# ③ 改代码，小步提交（提交信息守规范，见 2.4）
git add -A && git commit -m "feat(post): 帖子检索加分类过滤"
# ④ 推上去开 PR
git push -u origin feat/post-search-filter
#    → 去 GitHub 点 "Compare & pull request"，指派同事 review
# ⑥ review 通过后在 GitHub 点 Merge（建议 Squash and merge，历史干净）
# ⑦ 本地清理
git checkout main && git pull && git branch -d feat/post-search-filter
```

### 2.3 多仓 submodule 怎么协作（本项目特有，容易晕）
本项目是**根仓库(workspace) + 6 个子仓库(submodule)**。改子仓代码时：
```
1) 在【子仓内】开分支、改、PR、合并进该子仓的 main
2) 回【根仓库】, "前进指针"记录用了子仓的哪个版本, 再提交根仓库
```
```bash
# 1) 子仓内走完整 PR 流程（同 2.2），合并后：
cd campus-wall-ai && git checkout main && git pull
# 2) 根仓库前进该子仓指针
cd .. && git add campus-wall-ai && git commit -m "chore(submodule): 前进 ai 指针(帖子检索过滤)" && git push
```
> 子仓在 `main` 分支、根仓库在 `master`。**别跑 `git submodule sync`**（本项目用 SSH 别名，会搞乱）。新人首次：`git submodule update --init --recursive`。

### 2.4 提交信息规范（Conventional Commits）
格式 `类型(范围): 描述`，类型常用：`feat`(新功能)/`fix`(修bug)/`docs`(文档)/`refactor`(重构)/`test`(测试)/`chore`(杂务)。
例：`feat(ai): 意图识别加 mixed 类型` / `fix(post): 修复删除帖子缓存未清`。
> 好处：历史清晰、能自动生成更新日志、PR 一眼看懂改了啥。

## 3. 你的一天（日常开发节奏）

```
早上：git pull 拉最新 → 看看同事昨天合了什么
接到任务：开功能分支 feat/xxx
写代码：在 B机 改 Java 后端 → IDEA 用"后端·dev"配置启动(连 A机 dev 中间件) → 浏览器/小程序点点看
自测：① Java 跑 ./mvnw test  ② 改了 AI 检索/prompt 就 APP_ENV=test python -m evals.run 看指标没退步
提交：小步 commit(守规范) → push → 开 PR → @同事 review
合并：review 通过 → Merge → 删分支 → 回 main
```
**核心心法**：**小步提交、勤拉勤推、改完先自测再 PR**。

## 4. 两个人怎么不打架（协作约定）

1. **各自一套 dev 环境**：你用 `_a`(DB campus_wall_dev_a / Redis 1 / bucket campus-dev-a)，同事用 `_b`。互不污染。（test/prod 共用）
2. **一人一个功能分支**：永远别在同一个分支上两个人改；别直接推 main。
3. **互相 review**：对方的 PR 你扫一眼再点合并——既抓 bug 又互相懂对方在干嘛。
4. **勤同步**：每天 `git pull`，分支存活别超过 2~3 天（越久越容易冲突）。
5. **数据库迁移协调**：改表结构走 Flyway（`V4.x__xxx.sql`，版本号只增不改）；两人同时加迁移要约定版本号别撞。
6. **约定分工**：比如你管后端+AI、同事管前端+运营后台，减少改到同一文件。
7. **冲突了别慌**：`git pull` 出现冲突→打开冲突文件，`<<<<<<<` 和 `>>>>>>>` 之间二选一或都留→`git add`→继续。拿不准就喊对方一起看。

## 5. 从开发到上线（dev → test → prod）

```
功能在 dev 做好 → 合进 main
        │
        ▼
   部署到 test 环境验收：跑评测(python -m evals.run)、手测关键流程、同事走查
        │ 通过
        ▼
   发布到 prod：Java 后端用 systemd 重启(prod profile)、AI 服务在 A机 重建容器、
                前端 npm run build 产物到位、数据库迁移自动跑(Flyway)
```
**铁律**：**任何东西上 prod 前，必须先在 test 验过。** prod 只连真实数据，绝不混测试数据。

### 5.1 你改了 AI 仓库代码，怎么部署到 A机？（B机 → A机）

**先建立一个认知**：`campus-wall-ai` 这个 AI 服务**不在你 B机 跑**，它以 **2 个容器**常驻 **A机**（`campus-wall-ai` + `campus-wall-ai-worker`，镜像 `campus-wall-ai:2.0.0`），由 `campus-wall-ops/docker-compose.yml` 编排，镜像是在 **A机本地** 从 `build: ../campus-wall-ai` 构建的。

> 所以“部署” = 把最新代码弄到 **A机的仓库目录** → 在 **A机** 重建镜像并滚动重启容器。**不是**把 jar/包传过去——A机 自己会 build。

**一条命令搞定**（在 B机 `campus-wall` 仓根目录跑）：
```bash
bash deploy/server/deploy-ai.sh          # git 模式(默认,发布用)：A机 git pull 取你已 push 的代码 → 重建
bash deploy/server/deploy-ai.sh rsync    # rsync 模式(调试用)：把你本地未提交的 WIP 直接同步到 A机 → 重建
```
脚本做的事：① 校验 SSH 通 A机 → ② 送代码（git pull 或 rsync）→ ③ A机 `docker compose build ai-api` + `up -d --no-deps --force-recreate` 重启 ai-api/worker → ④ `curl :8011/health` 健康检查，失败自动打印日志。

**两种模式怎么选**：
| | git 模式（默认，推荐） | rsync 模式（临时调试） |
|---|---|---|
| 前提 | 你已**子仓 push + 根仓库前进指针 push**（守多仓铁律）| 不用 commit，直接同步本地工作树 |
| 版本可追溯 | ✅ A机 代码 = 某个 git commit | ❌ A机 是你本地的临时快照 |
| 适合 | 正式发布、要能回滚 | 验证一个改动通不通、快速试错 |

**手动等价命令**（脚本不可用时，SSH 进 A机自己敲）：
```bash
ssh nvidia@172.21.160.212
cd /home/nvidia/Desktop/campus-wall
git pull --ff-only && git submodule update --init --force campus-wall-ai   # 取根指针锁定的 AI 代码
cd campus-wall-ops
docker compose build ai-api
docker compose up -d --no-deps --force-recreate ai-api ai-memory-worker   # 重建并重启(不动 neo4j/redis/数据卷)
curl -s http://localhost:8011/health        # {"status":"ok",...} 即成功
```

**回滚**：git 模式部署前脚本会打印 `BEFORE_SHA`；要回滚就 `ssh A机 → cd campus-wall-ai → git checkout <BEFORE_SHA>` 再重跑重建段。

> ⚠️ B机 挂梯子/VPN 会让 `ssh 172.21.160.212` / rsync 卡死 → 配 `NO_PROXY` 或关梯子。
> ⚠️ 改了 prompt/检索/判定闸的，**部署前先在 A机 `APP_ENV=test python -m evals.run` 过一遍评测**，别把命中率/防幻觉基线改坏（见《Agent 开发与评测闭环指南》）。

### 5.2 Java 后端 / 前端 怎么“上线”？

它们**不需要部署到 A机**——Java 后端 prod 用 **systemd**（单元 `campus-wall-ops/deploy/campus-wall.service`）跑 jar；前端 `npm run build` 出产物交给 nginx。dev 阶段你在 B机 IDEA/微信开发者工具里直接跑，连 A机 中间件即可，无需“部署”这一步。

## 6. 小白避坑清单（都是真踩过的）

1. **别在 main 上直接改** → 开功能分支走 PR。
2. **别往 prod/共享库灌测试数据** → 造数只进你的 dev 或 test。
3. **改 prompt/检索前先跑评测留基线** → 否则不知道改好还是改坏。
4. **submodule 提交顺序别反** → 先子仓 PR 合并，再根仓库前进指针。
5. **B机 挂梯子会连不上 A机内网** → 配 NO_PROXY。
6. **密码别提交** → 只提交 `.env.*.example`，真实 `.env` 已 gitignore。
7. **Flyway 迁移版本号只增不改** → 已应用的脚本是"历史"，不能动。

## 7. 速查卡

```bash
# —— 日常 Git ——
git checkout main && git pull              # 拉最新
git checkout -b feat/xxx                   # 开分支
git add -A && git commit -m "feat(x): ..." # 提交
git push -u origin feat/xxx                # 推 + 开 PR
# 合并后
git checkout main && git pull && git branch -d feat/xxx

# —— 多仓(改了子仓后) ——
cd <子仓> && git checkout main && git pull
cd .. && git add <子仓> && git commit -m "chore(submodule): 前进指针" && git push

# —— 切环境 ——
# Java 后端: IDEA 选 profile(dev/test/prod) + 环境变量指 A机
# AI 服务:   APP_ENV=dev python ... (或 VSCode 选对应运行配置)
# 前端:      .env.local 改 VITE_API_BASE_URL

# —— 自测 ——
cd campus_wall && ./mvnw test              # Java 单测
cd campus-wall-ai && APP_ENV=test python -m evals.run   # AI 评测

# —— 环境连通性自检（开发前先验环境通不通）——
bash deploy/team-dev/check-connection.sh             # B机 devs：查端口可达(无需凭据)
python3 deploy/team-dev/check_env.py dev_b           # 管理员/A机：深度查具体库/RedisDB/Neo4j实例
#   可选环境：dev_a / dev_b / test / prod
```

> 不懂就问、拿不准就喊同事一起看——**协作的本质是沟通，不是 Git 命令背得多熟**。
