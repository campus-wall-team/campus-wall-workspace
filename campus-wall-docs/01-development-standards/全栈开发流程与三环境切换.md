# 全栈开发流程与三环境切换（dev / test / prod）

> 面向：第一次全面负责本项目、还不清楚开发流程的全栈同学。
> 读完你能答上来：① 这套系统由哪些服务组成、谁连谁；② 哪些中间件要隔离、为什么；
> ③ 每个服务怎么在 dev/test/prod 之间切换；④ 改一行代码到上线，完整流程怎么走。

## 1. 先建立全局观：你管的是「一套多服务系统」，不是一个程序

校园墙 = **6 个仓库 + 4 类中间件 + 3 个模型服务**。根仓库（workspace）用 git submodule 把各子仓聚在一起。

| 仓库 | 是什么 | 技术栈 | 端口 |
|---|---|---|---|
| `campus_wall` | **Java 主后端**（唯一对外 API，业务全在这） | Spring Boot 3 | 8080 |
| `campus-wall-ai` | **AI 服务**（LangGraph agent + RAG + AI 发帖） | Python FastAPI | 8011 |
| `campus-wall-frontend` | C 端**微信小程序**（学生用） | uni-app + Vue3 | — |
| `campus-wall-monitor-ui` | **运营后台**（管理员用） | Vue3 + Element Plus | 8090 |
| `campus-wall-data-pipeline` | 数据管道 | — | — |
| `campus-wall-ops` | 部署/监控（docker-compose、Grafana） | — | — |

**调用关系（记住这张图，调试全靠它）**：
```
小程序 ─┐
        ├─► Java 后端(8080) ──► MySQL / Redis / MinIO
运营后台 ┘        │
                 └─► AI 服务(8011) ──► Neo4j / bge-m3 / 35B / VLM
                        ▲
          (AI 代发帖时回调 Java /posts/publish)
```
关键约定：**前端只调 Java；AI 服务不直接对前端**。Java 是总入口，AI 是它的一个下游。

## 2. 哪些中间件需要环境隔离？（核心问题）

判断标准一句话：**「有状态的（存数据的）必须隔离，无状态的（纯算的）可以共享」。**
因为有状态的服务里存的是数据——dev/test/prod 的数据混在一起就会互相污染（测试帖被真实用户搜到、评测把生产数据改脏）。

### ✅ 必须隔离（有状态 = 存数据）

| 中间件 | 存什么 | 不隔离的后果 |
|---|---|---|
| **MySQL** | 帖子/用户/评论/AI记录（业务权威数据） | 测试造的假用户/假帖混进生产，数据脏 |
| **Neo4j** | 帖子向量 + 知识图谱（检索用） | 评测锚定帖被真实搜索命中（本项目踩过这个坑） |
| **Redis** | 缓存 / 记忆队列 / 会话 checkpoint | 测试的 key 冲掉生产缓存 |
| **MinIO** | 上传的图片等对象 | 测试图片占生产桶、URL 混乱 |

### 🆗 可以共享（无状态 = 只做计算，不存业务数据）

| 服务 | 为什么能共享 |
|---|---|
| **Qwen3.6-35B**（.101:8003）| 模型服务，无业务状态，输入什么算什么（生产若担心抢算力可单独部署，但不是数据隔离问题） |
| **bge-m3 / qwen2.5vl**（Ollama 11434）| 同上，纯推理 |
| 云端 DashScope | 同上 |

> 一句话结论：**本项目要隔离的是 MySQL、Neo4j、Redis、MinIO 这 4 个；模型服务 3 个可共享。**

### 本项目隔离现状（已落地 test）
- **Neo4j**：社区版单库 → test 用**独立容器** `campus-neo4j-test`（:7689），与 dev/prod(:7688) 物理隔离。✅
- **Redis**：用不同**逻辑库号**隔离（dev=DB 1 / test=DB 15 / prod=DB 0），同实例不同 namespace。
- **MySQL**：用不同 **schema/库名** 或不同实例隔离（test 可用独立 sqlite，不碰共享库）。
- **MinIO**：用不同 **bucket** 或不同实例隔离。

## 3. 三个环境是什么 & 每个服务怎么切换

### 3.1 三环境总览

| | dev（开发） | test（测试/评测） | prod（生产） |
|---|---|---|---|
| 谁用 | 你本地写代码 | 自动化测试/评测/上线前验证 | 真实用户 |
| 数据 | 假数据，随便清 | 干净、可复现的金标数据 | 真实数据，**碰都别碰测试** |
| MySQL | 共享 dev 库 / 本地 | 独立 test schema / sqlite | 生产库（GB10） |
| Neo4j | dev :7688 | **test :7689（独立容器）** | 生产实例 |
| Redis | DB 1 | DB 15 | DB 0 + AOF 持久化 |

### 3.2 每个服务怎么切环境（重点）

**所有服务的连接配置都是 `环境变量 / 配置文件` 驱动的，切环境 = 换一套配置，不改代码。**

#### ① Java 后端（campus_wall）——用 Spring Profile
```bash
# 配置文件: application.yaml(公共) + application-dev.yaml + application-prod.yaml
# 默认 profile 见 application.yaml: SPRING_PROFILES_ACTIVE 默认 dev
SPRING_PROFILES_ACTIVE=dev  mvn spring-boot:run     # 开发
SPRING_PROFILES_ACTIVE=prod java -jar app.jar       # 生产
```
中间件地址全是 `${变量:默认}`，可被环境变量覆盖（无需改 yaml）：
```bash
MYSQL_URL=jdbc:mysql://test主机:3306/campus_wall_test  \
REDIS_HOST=test主机  MINIO_ENDPOINT=http://test主机:9000 \
AI_SERVICE_BASE_URL=http://localhost:8011  java -jar app.jar
```
> test 环境就是再加一份 `application-test.yaml`（或一组 env 变量）指向 test 中间件。

#### ② AI 服务（campus-wall-ai）——用 .env 文件
```bash
# 三套模板: .env.dev.example / .env.test.example / .env.prod.example
cp .env.test.example .env.test            # 复制为实配(已 gitignore, 填好密码)
set -a; source .env.test; set +a          # 加载该环境
uvicorn app.main:app --port 8011          # 跑服务
# 或跑评测:
python -m evals.run                        # 此时连的是 .env.test 里的 test Neo4j(7689)
```
隔离点在 `.env.{env}`：`NEO4J_URI` / `REDIS_URL` 的 DB 号 / `DB_URL`。

#### ③ 前端（小程序 / 运营后台）——用 VITE_ 环境变量
```bash
# campus-wall-frontend(小程序) 和 monitor-ui 都用 vite
# .env.local 填 VITE_API_BASE_URL 指向「连哪个后端」
VITE_API_BASE_URL=http://localhost:8080      # dev: 连本地后端
VITE_API_BASE_URL=http://test主机:8080        # test
# 生产由 nginx 同源反代，前端只发相对路径 /api
```

### 3.3 环境切换速查表

| 服务 | 切换方式 | 改哪里 |
|---|---|---|
| Java 后端 | `SPRING_PROFILES_ACTIVE` + 环境变量 | `application-{env}.yaml` |
| AI 服务 | `source .env.{env}` | `.env.{dev,test,prod}` |
| 小程序/运营后台 | `VITE_*` | `.env.local` |

### 3.4 本项目已落地的环境矩阵（GB10 实配，照着用）

**机器分工（关键认知）**：中间件吃内存的活全交给 GB10，B 机器只写代码。
```
┌─ GB10  spark-ab42 / 172.21.160.212 / 121G 内存（用 26G，空 95G）──────────┐
│  所有中间件 + 模型都在这：                                                  │
│   MySQL :3306(一实例4个库) · Neo4j 7688/7689/7691(三实例) ·                │
│   Redis :6379(多 DB 号) · MinIO :9000(多 bucket) ·                        │
│   Ollama :11434(bge-m3/qwen2.5vl) · 35B 在另一台 .101:8003               │
└──────────────────────────────────────────────────────────────────────────┘
        ▲ 内网连接(172.21.160.212)
┌─ B 机器（内存小）─────────────┐
│  只写代码 + 跑你在改的那个服务  │   ← 一个中间件都不起
│  进程，连 GB10 的中间件         │
└───────────────────────────────┘
```
> 为什么这样：GB10 有 121G 内存、整个中间件栈才占 ~4G，完全放得下三套环境；B 机器内存小，就别在上面起中间件——连 GB10 即可。

**已建好的环境矩阵**（4 类中间件 × 各环境）：

| 环境 | 谁用 | MySQL 库 | Neo4j | Redis DB | MinIO bucket |
|---|---|---|---|---|---|
| **prod** | 真实用户（共享） | `campus_wall` | `:7688` campus-neo4j | 0 | `campus-wall` |
| **test** | 全队评测/CI（共享） | `campus_wall_test` | `:7689` campus-neo4j-test | 15 | `campus-test` |
| **dev（你）** | 开发 A | `campus_wall_dev_a` | `:7691` campus-neo4j-dev | 1 | `campus-dev-a` |
| **dev（同事）** | 开发 B | `campus_wall_dev_b` | `:7691`（共享） | 2 | `campus-dev-b` |

> MinIO 的 bucket 配 `MINIO_BUCKET=xxx` 即可，Java 启动时 `MinioUtil.ensureBucketExists()` 自动建；Redis 只是换 DB 号，不用建实例。

### 3.5 团队 2 个开发，怎么分环境？

**只有 dev 每人一套，test 和 prod 全队共用**（你的判断对）：

| 环境 | 几套 | 为什么 |
|---|---|---|
| **dev** | **每人一套**（已建 _a / _b） | dev 是"我的草稿本"——你跑 Flyway 迁移/造脏数据，不能影响同事 |
| **test** | **1 套共享** | 评测/验收要"同一把尺子"，每人一套就没法对比了 |
| **prod** | **1 套** | 线上只有一份，废话 |

所以 2 个开发 = 2 套 dev + 1 套 test + 1 套 prod（不是 2×3=6 套）。同事来了，照 `_a` 复制一份 `_b` 即可（库/Redis DB/bucket 换个后缀，dev Neo4j 7691 两人共享）。

### 3.6 你在 B 机器上具体怎么切环境

每个服务一份对应环境的配置，切=换配置：
```bash
# AI 服务（campus-wall-ai）
cp .env.dev.example .env.dev        # 首次：复制模板, 已指向 GB10 内网 IP
set -a; source .env.dev; set +a     # 切 dev
uvicorn app.main:app --port 8011    # 跑(连 GB10 的 dev Neo4j 7691)
# 切 test 跑评测：source .env.test 即可（连 7689 test 实例）

# Java 后端（campus_wall）—— 用 profile + 环境变量指向 GB10
SPRING_PROFILES_ACTIVE=dev \
MYSQL_URL='jdbc:mysql://172.21.160.212:3306/campus_wall_dev_a?characterEncoding=utf8&serverTimezone=Asia/Shanghai' \
REDIS_HOST=172.21.160.212 MINIO_ENDPOINT=http://172.21.160.212:9000 MINIO_BUCKET=campus-dev-a \
AI_SERVICE_BASE_URL=http://172.21.160.212:8011 \
./mvnw spring-boot:run

# 小程序 / 运营后台 —— .env.local 指向连得到的后端
echo 'VITE_API_BASE_URL=http://172.21.160.212:8080' > .env.local
```
> ⚠️ B 机器挂梯子/VPN 会劫持 172.21.x 内网连接（后端打印"agent 请求"后卡死）→ 配 `export NO_PROXY=localhost,127.0.0.1,172.16.0.0/12` 或关梯子。

### 3.7 用 IDEA / VSCode 一键切环境（配置就在仓库里）

**3 份环境配置就在仓库**：`campus-wall-ai/.env.dev.example` / `.env.test.example` / `.env.prod.example`（已提交）。
切换机制 = **一个环境变量 `APP_ENV`**：AI 服务的 `config.py` 启动时按 `APP_ENV` 自动加载 `.env.<env>`
（找不到本地实配则回退同名 `.example`）。所以你**不用手动 source、不用改代码**，IDE 里选一下就切了。

```bash
# 命令行：一个变量切环境
APP_ENV=dev  uvicorn app.main:app --port 8011    # dev
APP_ENV=test python -m evals.run                  # test 跑评测
# 想要个人覆盖：cp .env.dev.example .env.dev 再改（.env.dev 已 gitignore，优先于 .example）
```

**VSCode**（配置已提交 `campus-wall-ai/.vscode/launch.json`，开箱即用）：
- 打开 `campus-wall-ai` 文件夹 → 左侧"运行和调试"下拉，直接选：
  「AI 服务 · dev」「AI 服务 · test」「评测 · test」等——每个配置内置了对应 `APP_ENV`。
- 首次：`Ctrl+Shift+P → Python: Select Interpreter` 选 graphrag conda 环境。

**IntelliJ IDEA**：
- **Java 后端**：用 Spring Boot 运行配置里的 **Active profiles** 填 `dev`/`test`/`prod`（IDEA 原生支持），
  中间件地址用 **Environment variables** 填 `MYSQL_URL=...dev_a;MINIO_BUCKET=campus-dev-a;REDIS_HOST=172.21.160.212`。
- **Python（AI 服务）**：运行配置 → **Environment variables** 加一行 `APP_ENV=dev`（或 test/prod）即可。
  建 3 个运行配置（dev/test/prod）存为项目级，团队共享。

> 一句话：**配置在仓库（.env.*.example），切换靠 `APP_ENV` 一个变量，IDE 里点一下。**

## 4. 全栈开发日常流程（从零到提交）

### 4.1 首次搭环境
```bash
git clone <workspace 仓库>
cd campus-wall
git submodule update --init --recursive   # 拉所有子仓
# 各服务各自装依赖、配 .env、跑起来（见各子仓 README/CLAUDE.md）
```

### 4.2 日常改代码循环
```
①拉最新 → ②改代码 → ③本地跑起来手测 → ④跑自动化测试 → ⑤提交
```
- AI 服务跑测试：`cd campus-wall-ai && pytest -q`（全 mock，秒级）。
- Java 跑测试：`cd campus_wall && ./mvnw test`。
- 改了 prompt / 检索 / 判定逻辑 → **额外跑评测**：`source .env.test; python -m evals.run`，对比基线别退步。

### 4.3 多仓提交流程（submodule，容易搞错）
**顺序很重要：先提子仓、再前进根仓库指针。**
```bash
# 1) 在被改的子仓内提交并推送
cd campus-wall-ai && git add -A && git commit -m "feat: xxx" && git push origin main
# 2) 回根仓库, 前进该子仓的"指针"并提交
cd .. && git add campus-wall-ai && git commit -m "chore(submodule): 前进 ai 指针" && git push origin master
```
> ⚠️ 子仓在 `main` 分支、根仓库在 `master`。**别跑 `git submodule sync`**（本项目用 SSH 别名，sync 会搞乱）。

### 4.4 改数据库结构 → 走 Flyway 迁移
Java 后端的表由 Flyway 管：**只能新增 `V4.x__xxx.sql` 迁移脚本，版本号递增、不可改历史脚本**（已应用的迁移是不可变的）。

### 4.5 评测闭环（质量保障）
改完检索/prompt，跑 test 环境评测确认指标不退步（详见《Agent 开发与评测闭环指南》）：
```bash
cd campus-wall-ai && set -a && source .env.test && set +a && python -m evals.run
```

## 5. 新手最容易踩的坑（本项目真实发生过）

1. **别往 dev/prod 库灌测试数据** —— 评测/造数只进 test 实例（曾把锚定帖插进 prod Neo4j，被真实搜索看到）。
2. **写数据要注意双写一致** —— 帖子是 MySQL（权威）+ Neo4j（检索副本）双写；只写一边会产生「孤儿数据」（只在 Neo4j 的帖会被 Java hydrator 按 MySQL 过滤掉）。
3. **改 prompt/检索前先有评测基线** —— 否则是「盲改」，不知道改好还是改坏。
4. **submodule 顺序别反** —— 先提子仓推送，再前进根仓库指针。
5. **密码/密钥走环境变量** —— 只提交 `.env.*.example` 模板，真实 `.env` 一律 gitignore。
